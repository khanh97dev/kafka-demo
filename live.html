PARTITIONS

Vì sao thiết kế như vậy (thuật ngữ)

key = streamId
Mọi JOIN/LEAVE của 1 stream vào cùng 1 partition → tuần tự (per-key ordering) → đếm đúng. Đánh đổi: hot partition khi stream S1 quá lớn.
key = userId
JOIN/LEAVE của 1 user vẫn đúng thứ tự, tải chia đều hơn. Nhưng count của stream bị chia nhiều partition → cần cộng gộp (aggregate) — consumer đếm per-partition rồi merge, hoặc dùng Kafka Streams.
key = null
Round-robin: JOIN và LEAVE của cùng 1 user rơi vào 2 partition khác nhau, consumer khác nhau → LEAVE có thể đến trước JOIN → ghost viewer.
Consumer group
Mỗi partition chỉ 1 consumer. Thêm consumer chỉ hữu ích tới số partition.
Rebalance
Consumer join/leave/crash → group dừng ~1.5s, partition gán lại. Trong livestream nghĩa là count đứng im rồi nhảy.
Lag
LEO − committed. Raid 150 user làm lag vọt; viewer count hiển thị trễ.
Idempotent consumer
Dùng Set (userId) thay vì counter ±1 để xử lý trùng không làm count sai. Ở bảng trên "Set size" dựa trên Set.
Compaction
Topic state viewer-state (key = streamId:userId) bật log compaction chỉ giữ giá trị mới nhất; dùng để khôi phục state sau khi consumer restart.
